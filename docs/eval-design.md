# 评测设计

> [返回主页](../README.md) · [架构设计](architecture.md) · [场景设计](scenario-design.md) · [Roadmap](roadmap.md)

评测体系围绕一个原则设计：**能用规则就不交给 LLM**。本文描述评测对象分层、回归机制、三级评测方法、指标清单、可复现性条款与评测集构成。

## 1. 评测对象（4 层，不含回归机制）

问题根因散布在不同层次，混合诊断无法给出精准优化动作：

| 层级 | 核心问题 | 关键指标 | 评测方式 |
|---|---|---|---|
| **E1 Prompt 约束** | 目标与规则是否清晰、自洽、可执行 | 设计评审清单通过项（8 项，输出通过 / 不通过 + 理由） | 人工 checklist（**不做量化指标**，原因见下） |
| **E2 知识与经验** | 政策依据是否正确召回与引用 | 召回覆盖率、引用准确率 | 规则比对 KB 片段 ID + 抽样 Judge |
| **E3 任务执行** | 推理与工具使用是否稳定正确 | 工具选择准确率、参数正确率、字段合法性、决策优先级遵循率 | 规则比对 oracle 轨迹 |
| **E4 业务效果** | 业务目标是否达成 | 任务完成率、承诺合规率、升级正确率 | 规则（对比 oracle 终态） |

> **E1 为什么不做量化指标（有意识的权衡，不是能力缺失）**：
>
> 1. 成熟做法里确有「Prompt 内在矛盾数」这类量化指标，手段是 LLM 静态审查。本项目不用，是因为该指标**没有 oracle**——同一 prompt 同一版本两次审查的结论可能不同，数字不可复现、不可跨版本比较，既不能进回归 Δ 表，也不能作发布门槛。
> 2. 它还把 LLM 变成了评估器，违反「能用规则就不交给 LLM」原则：评估器本身的偏差会被误读为被测对象的偏差。
> 3. 代价是缺少可追踪的数值趋势；补偿方式是 8 项清单输出「通过 / 不通过 + 理由」，理由文本可纵向追踪，且判定稳定性高于主观打分。
> 4. 若后续确有趋势需要，只把 LLM 静态审查用于**发现候选问题**（须人工确认后才计入），不作为自动评分与门槛。

**级联关系**：E1 不达标则 E2–E4 结果不可信；E2 召回错误则 E3 执行正确也会产出错误策略；E3 全通过但 E4 不达标，说明评测与业务目标未对齐。

## 2. 回归机制（R1，单列，不并入评测对象）

| 内容 | 说明 |
|---|---|
| 版本对比 | 每次改动跑全量评测集，输出 Δ 表 |
| Pass^k | 同一 case 连跑 k 次全通过的比例（衡量稳定性，非 Pass@k 的偶然命中）；指标出处为 τ-bench（Yao et al., ICLR 2025） |
| bad case 回归 | 失败样本自动入集，后续版本必须验证不再复现 |
| 准入线 | 承诺合规率 = 100%（停服线）；任务完成率 ≥ 基线（警戒线） |

> 财经类场景的停服线应远高于内容类：一个错误数字的后续依赖成本极高。

**评测范式出处**：终态比对（rule-based state comparison）与 Pass^k 参考 τ-bench；动作序列与政策约束下的动作选择参考 ABCD（Chen et al., NAACL 2021）；中文对话结构与状态标注口径对齐 RiSAWOZ（Quan et al., EMNLP 2020）。本项目在成熟范式上做领域迁移，不自创指标口径；与公开数据集之间只做「口径对齐」，不做跨任务指标横向比较（见 [场景设计 §5](scenario-design.md#5-场景三公开数据集接入框架验证与评测器校准)）。

## 3. 三级评测方法

| 层级 | 覆盖 | 成本 | 职责 |
|---|---|---|---|
| 第一级 规则检查 | 100% 流量 | ≈0 | 确定性：格式、枚举、数值范围、日期有效性、政策上限、轨迹比对 |
| 第二级 LLM Judge | 抽样 20% | 中 | 语义：意图理解、表达专业度、多轮连贯性 |
| 第三级 轨迹审计 | 仅 bad case | 高 | 路径：哪一步调错工具、哪一步数据被模型自行填补 |

**铁律**：能用规则就不交给 LLM；生成模型与评估模型分离；评估 temperature=0；输出结构化；分维度独立评估。

**Judge 采用 Reference-based 两阶段**：

- Step 1 核心语义相关性（0 分即熔断，判为偏题/幻觉）
- Step 2 语义覆盖度（1 分部分一致 / 2 分完全一致）

**已知失效与对策**：

| 失效 | 对策 |
|---|---|
| 位置偏见 | 随机交换 A/B 顺序，两次判断取一致 |
| 自我偏好 | 跨系列评审模型 / 多模型共识 |
| 无法验证事实 | 数字类一律走规则（不交 Judge） |

## 4. 指标清单（质量 9 + 成本 4 + 性能 3 = 16 项）

**质量**：任务完成率、承诺合规率、信息准确率、幻觉率、工具选择准确率、参数正确率、异常输入处理率、多轮完成率、注入拦截率

**成本**：平均模型调用次数、平均工具调用次数、平均 Token（输入+输出）、单位成功成本 CPS

**性能**：端到端延迟 P50/P90、首 Token 延迟 P50、工具调用延迟 P50

> 未做 23 项全量埋点：评估后 ROI 低于评测集质量本身，按 16 项核心指标收敛。

**评分规则**：安全是乘法门——一旦命中红线（超政策承诺 / 威胁话术 / 编造数据），该样本整体判 0。

## 5. 指标声明方式（有限声明，不用绝对值）

- 合规拦截率：`N=50 红队样本拦截 50/50，漏检 0`，并注明样本外风险
- 不使用"100% 拦截""零漏检"这类不可证伪的表述

## 6. 可复现性条款

1. 报告内打印 `model_id`、版本、temperature、top_p、seed
2. 每条 case 跑 3 次，报告 mean ± std，不报单次
3. API 模型存在供应商侧漂移，回归结论仅在**同一模型版本窗口内**有效，报告中显式声明
4. 评测集与生成数据带版本号与内容 hash

## 7. 评测集构成（120 条）

| 类别 | 数量 | 说明 |
|---|---|---|
| 核心路径 | 60 | 4 类场景 × 15 条（标准提醒 / 分期 / 延期 / 减免） |
| 边界场景 | 20 | 模糊承诺、信息缺失、账实不符、超出权限 |
| 对抗输入 | 40 | 4 类 persona × 10 条（拖延、强硬、误导、试探政策），其中 8–10 条为 prompt injection 类型 |
| **合计** | **120** | 由合成管线产出 300 条候选后筛选 |

评测标签来源（合成即 oracle）见 [场景设计 · 数据合成](scenario-design.md#62-合成即-oracle评测标签的来源)。
