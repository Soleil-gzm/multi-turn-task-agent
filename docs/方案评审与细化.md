# 方案评审与细化设计

> [返回主页](../README.md) · [架构设计](architecture.md) · [场景设计](scenario-design.md) · [评测设计](eval-design.md) · [Roadmap](roadmap.md)
>
> 本文是设计层的收敛结论，回答四个问题：数据集怎么选（第 1 节）、契约怎么定（第 2 节）、细节怎么落（第 3 节）、什么时候做（第 4 节）。第 5 节给出与既有文档的一致性核对结果。

## 0. 摘要

1. **数据集**：采用「三集分工」方案——RiSAWOZ 接入做框架验证与状态跟踪子集校准，ABCD 与 τ-bench 只读参照（不接入数据），补足「动作序列 + 政策约束」与「评测方法论」两层。单一 RiSAWOZ 存在范式错配，全量接入则成本收益倒挂。
2. **契约**：契约先行。新增六份契约（数据 / 工具 / 配置 / 错误降级 / API / Trace）+ 一份安全契约（注入防护），均给出可校验的结构而非描述性文字。
3. **细节设计**：识别三条独立链路（离线合成 / 在线推理 / 评测），并用「契约 → 代码落位表」把每一层钉到具体目录与模块。
4. **节奏**：契约与只读参照前置到 W0，避免返工；W1 只承诺「状态跟踪子集」校准，不承诺与论文指标横向可比。

## 1. 数据集选型方案对比

### 1.1 选型标准

不是"找一个公开数据集接入"，而是每份数据必须承担**一个明确的校准职责**。据此定三条标准 + 一道硬门槛：

| 标准 | 问题 | 不合格表现 |
| --- | --- | --- |
| 范式同构 | 它的任务定义与框架是否同一类问题 | 指标算不出来，或关心的维度它没有 |
| 标注可用 | 有无可作 oracle 的状态 / 动作 / 终态标注 | 只有对话文本，没有标签 |
| 口径可移植 | schema 能否映射到场景配置 | 需要为它改核心代码 |

**硬门槛（一票否决）**：官方 train/dev/test 划分、License 允许研究与展示、规模 ≥ 评测集 120 条所需、数据可公开下载。

### 1.2 候选规模与范式

| 数据集 | 语言 | 范式 | 规模 | 承担职责 | 明确不承担 |
| --- | --- | --- | --- | --- | --- |
| [RiSAWOZ](https://github.com/2019DSR/RiSAWOZ) | 中 | DST + 槽填充 | 11.2K 对话 / 150K 话语 / 12 域（65% 单域、35% 多域） | 中文对话结构（省略、指代）、状态标注口径、E3 状态跟踪子集校准 | 动作序列合法性、政策约束、任务终态判定 |

**一句话分工**：RiSAWOZ 管「对话长什么样」，ABCD 管「流程怎么走」，τ-bench 管「怎么判断走对了」。

### 1.3 三套方案

#### 方案 A：单集接入（RiSAWOZ only）

只接入 RiSAWOZ，其余一律不引入。

- **适用场景**：只想证明「第三方数据能被配置化接入」；时间极紧的框架冒烟。
- **优点**：接入成本最低（单一适配器）；合规最简单；中文叙事一致；下载与版本冻结容易。
- **缺点（决定性问题）**：**范式错配**——RiSAWOZ 的正误定义是「槽位填对」，而本项目核心指标是「动作合法 + 终态达标 + 承诺合规」。它能校准「我理解对了吗」，校准不了「我做对了吗」，而后者是 E3/E4 的全部内容；同时 12 条转移、政策上限（分期 ≤ 3 / 延期 ≤ 30 / 减免 ≤ 10%）在 RiSAWOZ 中无对应物。
- **风险**：文档若写「与公开基线可对照」，会因指标不可比而被判定不严谨。

#### 方案 B：三集分工（接入 1 + 只读参照 2）— **推荐**

RiSAWOZ 接入承担框架验证与状态跟踪子集校准；ABCD、τ-bench 以「只读参照」方式使用，不接入数据。

- **适用场景**：个人/团队项目需要在有限周期内同时立住「框架通用性」与「评测方法论可信度」。
- **优点**：
  - 三层缺口全覆盖：对话结构（RiSAWOZ）、动作与政策（ABCD）、评测范式（τ-bench）
  - 只读参照不落数据，**不产生再分发义务**，合规成本≈0
  - pass^k、终态比对、模拟用户三项方法论可直接复用，省去自研设计成本；指标出处可标注
- **成本**（区分两类，避免低估）：
  - 只读参照（ABCD / τ-bench，仅阅读 + 对照清单，不接入数据）：约 1.5–2 天
  - **RiSAWOZ 实际接入（适配器 + 口径映射 + 评测器校准）：约 3–4 天**。隐性成本有三处：① 原始 schema 与 C1 case / oracle 结构不匹配；② 标注粒度不同（数据集是扁平槽位-值标注，本项目是 `(stage, round_no, offer_state)` 元组）；③ 需额外写映射层，且评测器要在映射后的口径上重新校准
- **缺点**：需要主动阅读两份论文并输出对照清单；ABCD / τ-bench 为英文，需做概念映射而非直接借用文本；RiSAWOZ 适配层是本方案唯一的新增工程面。
- **风险**：只读参照容易流于形式——对策是把对照结论落成可勾选清单（见第 4 节 W0 交付物），而不是读完了事。

#### 方案 C：全公开集接入（RiSAWOZ + SGD + CrossWOZ + ABCD + τ-bench + ToolBench）

把候选清单里所有可用数据集都接进框架。

- **适用场景**：以「多场景泛化」为第一卖点、且评测器已完全成熟的项目。
- **优点**：覆盖最广；泛化证据最强；可做跨集迁移分析。
- **缺点**：适配器数量与维护成本线性上升；每个数据集都要处理字段错位、split 差异、许可条款；口径移植难度高（SGD 是 schema 驱动，与 yaml 场景配置语义重叠但不一致）；总工作量估算为方案 B 的 3–4 倍，而边际校准收益在第三份之后急剧下降。
- **结论**：不选。取舍原则是「能覆盖缺口的最小数集」。

### 1.4 加权评分

权重：范式同构 0.35 / 标注可用 0.25 / 口径可移植 0.15 / 合规 0.15 / 成本 0.10（1–5 分）。

| 维度（权重） | 方案 A | 方案 B | 方案 C |
| --- | --- | --- | --- |
| 范式同构（0.35） | 2 | 5 | 5 |
| 标注可用（0.25） | 4 | 5 | 5 |
| 口径可移植（0.15） | 4 | 4 | 2 |
| 合规与许可（0.15） | 5 | 4 | 3 |
| 实现成本（0.10） | 5 | 3 | 1 |
| **加权总分** | **3.55** | **4.50** | **3.85** |

方案 B 在「范式覆盖」上拿满分，同时把成本控制在可接受区间，是唯一同时满足两条硬需求的方案：框架验证不被推迟、评测方法论有出处。

**方案 C 的工作量修正**：若按真实接入成本（每集 3–4 天）重算，C 约为 B 的 2–3 倍（B 的 3–4 天接入 + 1.5–2 天参照 ≈ 5–6 天；C 为 4 集以上接入 ≈ 12–16 天），而非原估的「3–4 倍」。这进一步强化了不选 C 的结论。

### 1.5 接入成本预算与降级预案

真实数据集接入的工期容易被低估，这里给出明确预算与触发降级的条件：

| 项 | 预算 | 超时判据 |
| --- | --- | --- |
| 数据下载与 split 冻结（含 hash 记录） | 0.5 天 | 官方数据无法稳定获取 |
| 适配器（原始 schema → C1 case / oracle） | 1.5 天 | — |
| 口径映射层（扁平槽位标注 → 元组状态） | 1 天 | 映射后丢失轮次级信息 |
| 评测器在映射口径上的校准 | 0.5–1 天 | 校准后判定与标注一致率 < 80% |
| **合计** | **3–4 天** | — |

**降级预案（写入 Roadmap，作为明确的分支而非失败）**：若 W1 第 3 天结束时适配器仍未跑通端到端，则降级为「只做口径对照文档」——产出 `docs/prior-art.md` 中的 RiSAWOZ 章节（字段映射表、粒度差异清单、哪些字段无法映射及原因），**不承诺实际接入**。此时框架验证退回 milktea 场景（零代码改动验证），评测器校准退回 ABCD 范式对照。降级后仍保留两项产出：口径对照结论 + milktea 的通用性验证。这比硬撑到 W1 结束仍未跑通更符合项目管理常识。

### 1.6 决策与随之而来的修订

**决策：采用方案 B。**

同时修订一处既有表述——原「规则评测器在公开测试子集上产出与公开基线可对照的数字」属于**过度承诺**，因为 DST 的 Joint Goal Accuracy 与本项目的任务完成率不可比。改为有限承诺：

> RiSAWOZ 接入用于验证两件事：① 第三方数据经配置适配器可端到端跑通（框架无关性）；② 规则评测器在其**状态跟踪子集**上的判定与人工标注一致。本项目不与 RiSAWOZ 论文的 Joint Goal Accuracy 做横向比较——任务定义不同，指标不可比。

明确「什么能比、什么不能比」比给一个不可比的数字更可靠。此修订已同步到 [场景设计](scenario-design.md#5-场景三公开数据集接入框架验证与评测器校准) 与 Roadmap。

### 1.7 合规约束

| 约束 | 落地方式 |
| --- | --- |
| 数据许可：RiSAWOZ（研究用途）、ABCD（ASAPP 研究用途）、τ-bench（MIT） | 不重新分发原始数据；`data/README.md` 注明出处、用途限制与获取方式 |
| 虚构数据 | 业务数据 100% 程序化生成，不含真实客户、合同、金额 |
| 引用规范 | 论文出处写入报告与文档（见 [评测设计 · 评测范式出处](eval-design.md#2-回归机制r1单列不并入评测对象)） |
| 对抗数据 | 注入样本人工构造，不复用任何真实对话 |

## 2. 工程契约规范

契约回答「具体长什么样」。缺失会导致三个后果：代码边界模糊、AI 辅助生成不准、对外讲解讲不细。**原则：契约先行，代码后写。**

优先级：P0（W0 定）、P1（W1–W2 定）、P2（有余力）。

### 2.1 契约清单

| 契约 | 定义什么 | 优先级 | 缺失后果 |
| --- | --- | --- | --- |
| C1 数据契约 | case / oracle / 合成中间产物 schema | P0 | 评测地基不稳，合成与评测器对不上 |
| C2 工具契约 | 入参 / 出参 / 错误码 | P0 | 返回值不统一，评测无法比对 |
| C3 配置契约 | scenario.yaml 字段与启动预检 | P1 | 配置错误到运行时才炸 |
| C4 错误与降级 | 每类故障的检测、恢复、可见表现、判定 | P0 | 故障注入无法验收 |
| C5 API 契约 | 请求 / 响应 / 错误码 / 幂等 | P1 | 服务化时接口反复改 |
| C6 Trace 契约 | 一条轨迹记录哪些字段 | P1 | bad case 无法归因 |
| C7 安全契约 | 注入防护分层与测试集 | P0 | 对抗场景无防护设计 |

### 2.2 C1 数据契约：case 与 oracle

```json
{
  "case_id": "REC-CORE-0012",
  "version": "v1",
  "layer": "core",
  "subtype": "installment",
  "difficulty": 2,
  "seed": 42,
  "init_state": {
    "contract_no": "HT-Y2026-012",
    "invoice_no": "INV-20260123",
    "amount": 380000,
    "due_date": "2026-08-15",
    "overdue_days": 45,
    "status": "unpaid"
  },
  "user_persona": {
    "type": "delay",
    "goal": "不给出任何明确付款日期",
    "max_rounds": 10
  },
  "oracle": {
    "expected_tool_sequence": [
      {"tool": "query_receivable", "required": true, "order": 1},
      {"tool": "query_policy", "required": true, "order": 2},
      {"tool": "record_promise", "required": true, "order": null}
    ],
    "expected_args": {
      "query_receivable": {"contract_no": "HT-Y2026-012"}
    },
    "forbidden_actions": ["promise_beyond_policy", "threaten", "fabricate_amount"],
    "expected_terminal": {
      "stage": "CLOSED",
      "promise": {"pay_date": "2026-11-15", "amount": 380000}
    },
    "max_rounds": 15
  },
  "tags": ["has_statement_diff", "invoice_missing"],
  "content_hash": "sha256:..."
}
```

**三个必须定死的判定边界**（不定死，评测结果不可复现）：

| 边界 | 规则 | 理由 |
| --- | --- | --- |
| 工具重复调用 | `required=true` 只要求「至少一次」，不惩罚重试；单独记「重复调用次数」指标 | 重试是正确行为 |
| 顺序 | 仅 `order != null` 校验相对顺序；`order=null` 表示任意位置 | 过度约束会把合法路径判错 |
| 部分完成 | 按达成维度给分（拿到日期但未记录 = 0.5），不二值化 | 二值化丢掉「接近成功」信号 |

### 2.3 C2 工具契约

统一返回封装，避免评测器为每个工具写特例：

```json
{
  "ok": true,
  "data": {},
  "error": null,
  "meta": {"latency_ms": 12, "source": "mock_db"}
}
```

失败时 `error` 为 `{"code": "TOOL_TIMEOUT", "msg": "...", "retryable": true}`，错误码枚举：`NOT_FOUND / INVALID_ARG / TOOL_TIMEOUT / INTERNAL_ERROR / DEGRADED`。

每个工具的 JSON Schema **同时用于三处**：模型 function calling、参数正确率评测、文档生成。

```yaml
name: query_receivable
description: 查询指定合同号的应收账款信息（金额、账期、逾期天数、发票状态）
parameters:
  type: object
  properties:
    contract_no: {type: string, pattern: "^HT-Y2026-\\d{3}$"}
  required: [contract_no]
returns: ReceivableRecord
error_codes: [NOT_FOUND, INVALID_ARG, TOOL_TIMEOUT, INTERNAL_ERROR]
```

### 2.4 C3 配置契约与启动预检

`scenario.yaml` 用 pydantic 建模，启动时校验三项，**失败即 fail-fast，不静默降级**：

1. 必填字段齐全，`tools[].impl` 路径可导入
2. 转移表 `from` / `to` 均存在于 `stages`，无孤立状态、无不可达状态
3. `policy` 数值合法（`max_installments ≥ 1`、`max_extension_days ≥ 0`、`0 ≤ max_waiver_ratio ≤ 1`）

转移条件采用**受限表达式白名单**（比较运算 + 明确的槽位名），不使用 `eval`，避免配置层成为注入面。

### 2.5 C4 错误处理与降级矩阵（契约 7 类 / MVP 3 类）

| 故障 | 检测 | 恢复 | 用户可见 | 评测判定 |
| --- | --- | --- | --- | --- |
| 工具超时（> 3s） | timeout | 重试 1 次 → 仍失败降级 | 「正在查询，稍等」 | 记「重试成功 / 降级」 |
| 工具 500 | status code | 重试 2 次（指数退避）→ 降级 | 「系统繁忙，稍后核实」 | 不判失败，记入可用性 |
| 返回 schema 错 | pydantic 校验 | 弃用该数据，追问或换工具 | 正常对话 | 记「参数校验失败」 |
| 返回矛盾数据 | 交叉校验（金额 vs 对账单） | 以 `query_receivable` 为准，主动告知差异 | 「系统显示 X，您说 Y」 | **加分项** |
| 模型输出非法 JSON | 解析失败 | 重试 1 次（带纠错提示）→ 转纯文本解析 | 无感知 | 记「格式容错」 |
| 上下文超限 | token 计数超阈值 | 摘要压缩早期轮次，保留槽位 | 无感知 | 记「压缩触发次数」 |
| 用户注入指令 | 输入检测 + 输出校验 | 忽略越权指令，回归任务 | 正常对话 | 记「注入拦截」（防护分层见 C7） |

**范围口径（统一数字，全文一致）**：

- **契约定义 7 类故障**的可降级路径（检测 / 恢复 / 判定）：上表 7 行。
- **MVP 实现 3 类**：工具超时 / 工具 500 / 返回 schema 错——这三类覆盖主要降级路径。
- **其余 4 类**：矛盾数据 / 非法 JSON / 上下文超限 / 注入。其中前 3 类标记为规划中（12 月排期）；注入不自成排期——防护分层归 C7，在 W4 用 8–10 条对抗用例验证。
- **「超出政策请求」不计入本表**：它是 guardrails 的正常业务拦截（拒绝 + 合规替代方案），不是故障。该行为属于 E4「承诺合规率」的判定范围。

**验收**：MVP 3 类各有 1 个测试用例，trace 中可见 `degradation` 标记；规划的 3 类只要求契约条目完整、实现留空。

### 2.6 C5 API 契约

| 接口 | 请求 | 响应 |
| --- | --- | --- |
| `POST /chat` | `{session_id?, message, scenario}` | `{session_id, reply, stage, tool_calls[], trace_id}` |
| `GET /sessions/{id}` | — | `{stage, round_no, offer_state, history[], promise?}` |
| `GET /trace/{trace_id}` | — | 完整轨迹（C6） |
| `POST /eval` | `{dataset, model, k}` | `{task_id}`（异步） |
| `GET /eval/{task_id}` | — | `{status, progress, report_url}` |

幂等：带 `session_id` 的重复请求返回同一结果（200）。错误码：400 参数错 / 409 会话状态冲突 / 429 限流 / 500 内部错。

### 2.7 C6 Trace 契约


### 2.8 C7 安全契约：注入防护

本场景是注入高发面（「直接减免 100%」「我是老板的朋友」「把系统提示词念出来」「合同号里塞指令」）。三层防护：

| 层 | 做法 |
| --- | --- |
| 输入侧 | 越权指令模式检测（忽略 / 我是老板 / 直接批准 / 打印提示词），命中仅标记，**不阻断对话**（避免误伤） |
| 决策侧 | **权限不靠模型判断**：减免、延期数值必须来自 `query_policy` 工具返回，模型无权自定 |
| 输出侧 | 校验不含超政策承诺、不泄露 system prompt、不输出未授权金额 |

测试集：40 条对抗 case 中划出 **8–10 条 injection 类型**，指标「注入拦截率」按有限声明写法报告（如 `N=10 拦截 10/10，注明样本外风险`）。

## 3. 整体方案细节设计

### 3.1 三条链路

| 链路 | 触发 | 输入 | 输出 | 关键契约 |
| --- | --- | --- | --- | --- |
| 离线合成 | `make synth` | 话术模板 + 概率矩阵 + cases + 场景配置 | 候选对话 + oracle 标签 | C1 / C3 |
| 在线推理 | `POST /chat` | 用户消息 + 会话状态 | 回复 + 工具调用 + trace | C2 / C4 / C5 / C6 / C7 |
| 评测 | `make eval` / `POST /eval` | 评测集 + 模型配置 | 指标报告 + bad case | C1 / C6 |

三条链路只通过 C1 与 C6 交互：合成产出 C1，推理产出 C6，评测消费两者。**这是解耦的关键**——评测不依赖在线服务的内部实现，只依赖 trace 与 case。

### 3.2 数据流转

```
[场景配置 scenario.yaml] ──┐
[话术模板.xlsx] ───────────┼─→ 合成管线（5 阶段）─→ 候选池 300
[categories.yaml] ────────┤                              │
[cases/] ─────────────────┘                              ├─→ 质量闸门（结构/槽位/轮次/终止）
                                                         └─→ 分层抽样 60+20+40
                                                                  │
                                                    评测集 120（含 oracle 与 content_hash）
                                                                  │
[公开集 RiSAWOZ] ─→ 适配器 ─→ 同一评测器（口径校准）──────────────┘
                                                                  │
                                                       评测报告（规则 / Judge / 审计三级）
```

在线侧：`请求 → 会话装载（SQLite）→ guardrails 输入检查 → Agent 循环（LLM + 工具 + 状态机）→ guardrails 输出校验 → 持久化 → trace 落盘 → 响应`。

### 3.3 模块划分与依赖方向

```
services / mcp          ← 入口层（不反向依赖）
   ↓
agent                   ← 编排层（ReAct + 上下文工程）
   ↓
state / tools / guardrails / retrieval   ← 能力层（互不依赖，仅依赖 core）
   ↓
core                    ← 配置加载、注册表、日志、随机服务（最底层，零业务）
```

- **依赖只向下**：入口层不允许被能力层反向引用，避免循环依赖。
- **适配器隔离**：`src/adapters/{risawoz}/` 只依赖 `core` 与 C1 schema，数据源差异不进入 agent 层。
- **synthesis 与 eval 并列**：二者只依赖 `core` + 契约，不依赖 `services`，可离线独立运行。
- **零业务分支**：`agent` / `state` / `tools` 中不出现 `if scenario == ...`，差异全部来自 yaml。

### 3.4 契约 → 代码落位

| 契约 | 落位 | 校验方式 |
| --- | --- | --- |
| C1 数据 | `eval/datasets/**/*.jsonl` + `src/eval/contracts.py`（pydantic） | 加载即校验，`make test` 覆盖 |
| C2 工具 | `src/tools/{scenario}/*.py` + `src/tools/registry.py` | schema 与注册表一致性单测 |
| C3 配置 | `configs/scenarios/*.yaml` + `src/core/config.py` | 启动预检，失败退出码非 0 |
| C4 降级 | `src/agent/loop.py` + `src/tools/wrapper.py` | MVP 3 类 × 1 用例；契约覆盖 7 类，规划中的 3 类只校验条目存在 |
| C5 API | `src/services/app.py` | 契约测试（状态码 / 幂等 / schema） |
| C6 Trace | `src/core/trace.py` + `eval/reports/traces/` | 字段完整性与枚举校验 |
| C7 安全 | `src/guardrails/{input,output,policy}.py` | injection 8–10 条用例 |

### 3.5 关键技术实现路径

| 技术点 | 实现路径 | 验证方式 |
| --- | --- | --- |
| 状态机 | 转移表 yaml → 受限条件求值 → `(stage, round_no, offer_state)` 元组 | 12 条转移各 1 个单测；不可达状态检查 |
| Agent 循环 | ReAct + function calling；工具 schema 由 C2 生成；每步写 trace | 轨迹与 oracle 序列比对 |
| 检索 | jieba 分词手搓 BM25，接口协议化；可选向量 + RRF 融合 | 召回覆盖率 + 引用片段 ID 准确率 |
| 合成管线 | 声明式组装 → 概率矩阵 → 路径生成（A/B 集约束、自循环上限）→ 对话构建（继承链 / 多选项 / 占位符）→ 案例池 | 质量闸门 4 项指标 |
| 评测器 | 规则（100%）→ Judge（抽样 20%，Reference-based 两阶段）→ 审计（bad case） | 公开集校准 + 人工抽检 20 条 |
| 持久化 | SQLite：sessions / steps / promises；重启可恢复 | 杀进程重启后继续会话 |
| 可观测 | trace JSONL + `trace_id`，报告内嵌成本与延迟 | `GET /trace/{id}` 可回放 |

### 3.6 性能与容量估算

| 项 | 口径 | 目标 / 估算 |
| --- | --- | --- |
| 在线延迟 | 端到端 P50 / P90 | 记录并纳入报告；工具超时阈值 3s |
| 全量评测工作量 | 120 case × k=3 × 场均 10 轮 × 约 1.5 次 LLM 调用 | 约 5.4K 次调用/轮全量评测，需异步任务（C5 的 `POST /eval`） |
| 成本 | 单位成功成本 CPS | 每次报告输出，随模型对照表一并给出 |
| 存储 | 会话 + trace JSONL | 单会话 trace < 1MB，SQLite 单文件足够 |

## 4. 阶段划分与交付物

### 4.1 划分依据

1. **契约先行**：契约是 AI 辅助编码的输入，同一需求给不给 schema，产出质量差一个量级；且契约变更会连锁影响合成管线与评测器，越晚改越贵。
2. **只读参照前置**：ABCD / τ-bench 只需阅读与对照，1.5–2 天完成，但能避免 W2 发现状态机设计缺陷后返工。
3. **有限承诺前置**：W1 就写死「只校准状态跟踪子集」，避免验收口径在 W4 才暴露问题。
4. **不增加总工作量**：只调顺序与产出形态，不新增数据集接入。

### 4.2 工作流 × 阶段矩阵

| 阶段 | 数据集选型 | 工程契约 | 细节设计 |
| --- | --- | --- | --- |
| W0 | 定案方案 B；产出 prior-art 对照清单 | C1 / C4 / C7（P0） | 三条链路与依赖方向定稿 |
| W1 | RiSAWOZ 适配落地：3–4 天预算（下载冻结 0.5 + 适配器 1.5 + 口径映射 1 + 评测器校准 0.5–1）；第 3 天未跑通即触发降级预案（仅保留口径对照文档） | C2 / C3 / C6 | agent 循环 + 状态机 + trace 落地 |
| W2 | ABCD 对照检查 8 模块 / 12 转移 | C5 + 合成质量闸门 | receivables 合成管线 + 工具层 |
| W3 | 评测器在公开集与自造集双轨验证 | 抽样算法 + Judge prompt/rubric | 评测链路 + 报告生成 |
| W4 | 对抗 persona 参照 τ-bench 模拟用户 | 契约冻结与版本记录 | README 叙事 + 演示界面 |

### 4.3 交付物与验收标准

| 阶段 | 交付物 | 验收标准 |
| --- | --- | --- |
| W0 | `docs/prior-art.md`（三集对照清单：action 粒度 / policy 字段 / AST 轨迹比对 / pass^k）；C1 / C4 / C7 契约文档 | 清单可逐项勾选；契约 schema 能被 pydantic 加载并通过单测 |
| W1 | `configs/scenarios/risawoz.yaml` + 适配器 + `SCENARIO=risawoz make demo` + 首张校准报告 | 端到端跑通；状态跟踪子集判定与标注一致；**不与论文 JGA 横向比较**。第 3 天未跑通则触发降级（见 1.5），交付口径对照文档而不硬撑 |
| W2 | receivables 数据层 + 合成 50 条 + 12 转移单测 + milktea 场景 + `SCENARIO=receivables / milktea make demo` | receivables 跑通；**milktea 满足 4 条能力验证**（见下）；ABCD 对照清单无未解释差异项；合成质量闸门 4 项达标 |
| W3 | 120 条评测集 + 规则评测器 + v0 报告 + 人工抽检记录 | `make eval` 一条命令出报告；抽检 20 条 oracle 一致率 ≥ 90%；弱模型对照分数明显下降 |
| W4 | Judge 校准 30 条 + 对抗集（含 8–10 条 injection）+ v0/v1 对比报告 + 故障注入 3 类 | 注入拦截率按有限声明报告；每类故障用例可复现且 trace 有降级标记 |

**milktea 通用性验证的 4 条硬标准（「换 yaml 能跑通」不算通过）**：

1. **零代码改动**：`git diff` 不触及 `src/core`、`src/agent`、`src/state`、`src/tools`；只新增 `configs/scenarios/milktea.yaml`、`configs/prompts/milktea/` 与 `data/` 下的数据
2. **无业务分支**：`grep -R "milktea\|receivables" src/` 输出为空——`src/` 下不存在任何场景名字面量，业务差异 100% 来自配置
3. **状态机同引擎**：两场景的 `stages` / `transitions` 均由 yaml 定义；milktea 至少走完 3 个 stage 与 1 个异常分支（升级或拒绝），并产出与 receivables **同一 schema** 的 trace
4. **差异可列举**：输出两场景转移表的逐行 diff，证明每一处差异都能由 YAML 字段表达，不存在需要代码兜底的项

**判为不通过的反例**：需要改框架代码才能跑通；只换显示名但沿用同一转移表；trace schema 与 receivables 不一致；异常分支靠硬编码。
