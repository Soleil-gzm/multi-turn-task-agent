# 场景设计

> [返回主页](../README.md) · [架构设计](architecture.md) · [评测设计](eval-design.md) · [Roadmap](roadmap.md)

业务主线场景为 **B2B 应收账款协商**。场景搭建遵循「公开标准数据集优先」的选型原则：框架验证与评测器校准使用公开数据集场景 RiSAWOZ，业务规则注入验证使用 milktea；公开集不覆盖的领域贡献（应收账款协商与合成管线）由自造数据承担。本文描述场景选型依据、模块语义、政策边界、虚拟数据规范与数据合成管线。

## 1. 场景选型

任务型对话场景需要三样地基，应收账款协商天然具备：

| 地基  | 具体体现                     | 工程意义                 |
| --- | ------------------------ | -------------------- |
| 有单据 | 合同号、发票号、对账单、付款流水         | 工具层有真实对象可调，返回值可交叉校验  |
| 有规则 | 账期、逾期天数、政策边界（分期/延期/减免上限） | 状态机与护栏可落地            |
| 有判据 | 是否获取明确付款日期 + 金额          | 评测有客观 oracle，不依赖主观打分 |

对比"会员回访"类 B2C 场景：无业务单据、成功判据模糊、3–5 轮即结束——状态机无意义、评测无区分度。该类场景不作为业务主线：milktea 用于验证业务规则注入（见第 4 节），框架验证与基准校准由公开数据集场景 RiSAWOZ 承担（见第 5 节）。

## 2. 场景一：应收账款协商（主线）

### 2.1 角色与任务

- **Agent**：AI 财务专员「小账」
- **对话对象**：企业财务 / 采购负责人
- **任务**：协商逾期 30–90 天账款的付款安排
- **成功判据**：获取明确付款日期 + 金额，并成功记录
- **失败判据**：超政策承诺、威胁性话术、编造未提供的单据数据

### 2.2 模块划分（8 个）

8 个模块对应状态流转的功能单元：

| 模块        | 所属集合     | 语义                      |
| --------- | -------- | ----------------------- |
| 身份核实      | 起始       | 核实对接人与企业身份、确认单据归属       |
| 账款告知      | 过程       | 告知合同号、发票号、逾期天数、应还金额     |
| 异议澄清      | 过程       | 处理"已付款""金额不符""发票未收到"等异议 |
| 对账差异      | 过程       | 发现账实不符，触发差额核对           |
| 条件协商      | 过程       | 提出/回应分期、延期、减免方案         |
| 承诺确认      | 过程（触发再见） | 确认具体日期与金额，写入承诺记录        |
| 升级人工      | 例外       | 超出政策边界或客户拒绝对话           |
| 已结清 / 已记录 | 终止       | 协商闭环                    |

### 2.3 政策边界（红线）

| 项    | 约束                    |
| ---- | --------------------- |
| 分期期数 | ≤ 3 期                 |
| 延期天数 | ≤ 30 天                |
| 减免比例 | ≤ 10%                 |
| 禁止话术 | 威胁、伪造法律后果、承诺超出权限、编造金额 |

## 3. 虚拟数据规范

数据 100% 虚构，不含任何真实客户、真实合同或真实金额：

- **虚构企业（4 家）**：恒信精密制造、蓝湾食品、启衡科技、瑞和物流
- **合同号规则**：`HT-Y2026-0xx`
- **发票号规则**：`INV-20260xxx`
- **账期档位**：30 / 45 / 60 / 90 天
- **金额分布**：单笔 8 万–80 万，逾期 30–90 天
- **脏数据比例 30%**：缺发票号、账期与到期日不一致、金额单位混用（元/万元）、对账差额未标注

## 4. 场景二：milktea（通用性验证）

验证「业务规则全部由 yaml 注入」：换场景 = 换一个 yaml + 一份数据。

**验收标准（硬性，4 条，「能跑通」不算通过）**：

1. **零代码改动**：`git diff` 不触及 `src/core`、`src/agent`、`src/state`、`src/tools`，只新增场景 yaml、prompt 目录与数据
2. **无业务分支**：`grep -R "milktea\|receivables" src/` 输出为空，`src/` 下不存在场景名字变量
3. **状态机同引擎**：两场景的 stages / transitions 均由 yaml 定义；milktea 至少走完 3 个 stage 与 1 个异常分支，trace schema 与 receivables 一致
4. **差异可列举**：两场景转移表逐行 diff，每处差异都能由 YAML 字段表达

反例：需改框架代码才能跑通、只换显示名沿用同一转移表、异常分支靠硬编码——均判为不通过。

## 5. 场景三：公开数据集接入（框架验证与评测器校准）

采用「三集分工」，版本见 [方案评审与细化 · 数据集选型](方案评审与细化.md#1-数据集选型方案对比)。三份数据承担不同职责，不是互相替代：

| 数据集        | 范式               | 使用方式   | 承担职责                              | 明确不承担          |
| ---------- | ---------------- | ------ | --------------------------------- | -------------- |
| RiSAWOZ（中） | DST + 槽填充        | **接入** | 中文对话结构与状态标注口径；E3 状态跟踪子集校准；框架无关性验证 | 动作序列、政策约束、任务终态 |
| ABCD（英）    | 动作序列 + 政策约束      | 只读参照   | 8 模块 / 12 转移的合理性对照；policy 字段完备性   | 中文表达           |
| τ-bench（英） | 工具调用 + 政策 + 模拟用户 | 只读参照   | 终态比对、pass^k、模拟用户设计、政策文档组织         | 中文、本业务字段       |

**RiSAWOZ 接入的三项职责**：

1. **框架验证**：第三方数据经同一套配置适配器接入并端到端跑通，证明配置驱动不以自造数据为前提
2. **口径对齐**：receivables 的 case / 状态 / 标注格式向 RiSAWOZ schema 靠拢，控制自造数据的不规范风险
3. **评测器校准**：规则评测器先在公开集上对齐口径，再用于验收自造场景数据

**验收标准（硬性，有限承诺）**：`SCENARIO=risawoz make demo` 跑通；规则评测器在其**状态跟踪子集**上的判定与标注一致。本项目**不与论文的 Joint Goal Accuracy 横向比较**——DST 的任务定义与本项目的动作 / 终态判定不同，指标不可比。

**接入方式**：`configs/scenarios/risawoz.yaml` + 数据适配器（官方数据 → 框架 schema），核心代码零改动。

**预算与降级**：接入预算 3–4 天（下载与 split 冻结 0.5 + 适配器 1.5 + 口径映射 1 + 评测器校准 0.5–1）。第 3 天仍未跑通则降级为只做口径对照文档（字段映射表 + 粒度差异清单 + 无法映射项），通用性验证由 milktea 承担——明细见 [方案评审与细化 §1.5](方案评审与细化.md#15-接入成本预算与降级预案)。

**许可**：三份数据均不重新分发原始数据，仅作方法论对照与评测器校准；出处与用途限制见 `data/README.md`。

## 6. 数据合成

### 6.1 合成管线

```
话术模板.xlsx + categories.yaml
        │
        ├─→ 概率矩阵生成（模块权重 → 转移概率）
        │
        ├─→ 路径生成（A/B 集合约束 + 终止/自循环 + 重复次数上限）
        │
        ├─→ 对话构建（继承链 + 多选项 + 占位符 + 促销/施压插入 + 再见终止）
        │
        └─→ 案例池（字段定义 + 脏数据变体）
                     │
                     └─→ 多轮对话（JSON，含真实工具返回值）
```

关键能力：**配置驱动**。换场景只替换 `话术模板.xlsx`、`categories.yaml`、`cases/`、
`system prompt`，合成层代码不改。

### 6.2 合成即 oracle（评测标签的来源）

多轮对话的评测标签**不使用人工标注**，由合成管线程序化产出：

| 标签              | 来源                |
| --------------- | ----------------- |
| 期望工具调用序列        | 生成路径本身即期望轨迹       |
| 期望参数（合同号/金额/日期） | case 字段构造时已知      |
| 终态（是否达成承诺）      | 路径终止模块即终态         |
| 政策合规标签          | 生成时即校验过 policy 边界 |
| 边界样本（缺字段/脏数据）   | 按比例注入的变体          |

因此评测集不是逐条手写，而是**配好 oracle 后从候选池中按分层构成筛选**（构成方式见 [评测设计](eval-design.md#7-评测集构成120-条)）。标签程序化生成，使评测集可以随场景配置低成本重建。

### 6.3 数据局限

1. 全部数据为合成，不反映真实企业的账款分布与话术习惯
2. 政策边界为公开资料整理的简化模型，非任何真实机构的制度
3. 客户异议表达由模板组合生成，多样性低于真实通话
4. 未覆盖多语言、方言、口音、打断等语音场景
