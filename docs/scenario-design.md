# 场景设计

> [返回主页](../README.md) · [架构设计](architecture.md) · [评测设计](eval-design.md) · [Roadmap](roadmap.md)

框架首个落地场景为 **B2B 应收账款协商**；第二个场景 milktea 仅用于验证配置驱动的通用性。本文描述场景选型依据、模块语义、政策边界、虚拟数据规范与数据合成管线。

## 1. 场景选型

任务型对话场景需要三样地基，应收账款协商天然具备：

| 地基 | 具体体现 | 工程意义 |
|---|---|---|
| 有单据 | 合同号、发票号、对账单、付款流水 | 工具层有真实对象可调，返回值可交叉校验 |
| 有规则 | 账期、逾期天数、政策边界（分期/延期/减免上限） | 状态机与护栏可落地 |
| 有判据 | 是否获取明确付款日期 + 金额 | 评测有客观 oracle，不依赖主观打分 |

对比"会员回访"类 B2C 场景：无业务单据、成功判据模糊、3–5 轮即结束——状态机无意义、评测无区分度。该类场景在本框架中仅作为**通用性验证用例**保留（见第 4 节）。

## 2. 场景一：应收账款协商（主线）

### 2.1 角色与任务

- **Agent**：AI 财务专员「小账」
- **对话对象**：企业财务 / 采购负责人
- **任务**：协商逾期 30–90 天账款的付款安排
- **成功判据**：获取明确付款日期 + 金额，并成功记录
- **失败判据**：超政策承诺、威胁性话术、编造未提供的单据数据

### 2.2 模块划分（8 个）

8 个模块对应状态流转的功能单元：

| 模块 | 所属集合 | 语义 |
|---|---|---|
| 身份核实 | 起始 | 核实对接人与企业身份、确认单据归属 |
| 账款告知 | 过程 | 告知合同号、发票号、逾期天数、应还金额 |
| 异议澄清 | 过程 | 处理"已付款""金额不符""发票未收到"等异议 |
| 对账差异 | 过程 | 发现账实不符，触发差额核对 |
| 条件协商 | 过程 | 提出/回应分期、延期、减免方案 |
| 承诺确认 | 过程（触发再见） | 确认具体日期与金额，写入承诺记录 |
| 升级人工 | 例外 | 超出政策边界或客户拒绝对话 |
| 已结清 / 已记录 | 终止 | 协商闭环 |

### 2.3 政策边界（红线）

| 项 | 约束 |
|---|---|
| 分期期数 | ≤ 3 期 |
| 延期天数 | ≤ 30 天 |
| 减免比例 | ≤ 10% |
| 禁止话术 | 威胁、伪造法律后果、承诺超出权限、编造金额 |

## 3. 虚拟数据规范

数据 100% 虚构，不含任何真实客户、真实合同或真实金额：

- **虚构企业（4 家）**：恒信精密制造、蓝湾食品、启衡科技、瑞和物流
- **合同号规则**：`HT-Y2026-0xx`
- **发票号规则**：`INV-20260xxx`
- **账期档位**：30 / 45 / 60 / 90 天
- **金额分布**：单笔 8 万–80 万，逾期 30–90 天
- **脏数据比例 30%**：缺发票号、账期与到期日不一致、金额单位混用（元/万元）、对账差额未标注

## 4. 场景二：milktea（通用性验证）

仅用于证明「换场景 = 换一个 yaml + 一份数据」。

**验收标准（硬性）**：`SCENARIO=milktea make demo` 能跑通完整多轮对话。
不满足此标准，则"配置驱动"的架构主张不成立——该场景必须可演示。

## 5. 数据合成

### 5.1 合成管线

```
话术模板.xlsx + categories.yaml
        │
        ├─→ 概率矩阵生成（模块权重 → 转移概率）
        │
        ├─→ 路径生成（A/B 集合约束 + 终止/自循环 + 重复次数上限）
        │
        ├─→ 对话构建（继承链 + 多选项 + 占位符 + 促销/施压插入 + 再见终止）
        │
        └─→ 案例池（字段定义 + 脏数据变体）
                     │
                     └─→ 多轮对话（JSON，含真实工具返回值）
```

关键能力：**配置驱动**。换场景只替换 `话术模板.xlsx`、`categories.yaml`、`cases/`、
`system prompt`，合成层代码不改。

### 5.2 合成即 oracle（评测标签的来源）

多轮对话的评测标签**不使用人工标注**，由合成管线程序化产出：

| 标签 | 来源 |
|---|---|
| 期望工具调用序列 | 生成路径本身即期望轨迹 |
| 期望参数（合同号/金额/日期） | case 字段构造时已知 |
| 终态（是否达成承诺） | 路径终止模块即终态 |
| 政策合规标签 | 生成时即校验过 policy 边界 |
| 边界样本（缺字段/脏数据） | 按比例注入的变体 |

因此评测集不是逐条手写，而是**配好 oracle 后从候选池中按分层构成筛选**（构成方式见 [评测设计](eval-design.md#7-评测集构成120-条)）。标签程序化生成，使评测集可以随场景配置低成本重建。

### 5.3 数据局限

1. 全部数据为合成，不反映真实企业的账款分布与话术习惯
2. 政策边界为公开资料整理的简化模型，非任何真实机构的制度
3. 客户异议表达由模板组合生成，多样性低于真实通话
4. 未覆盖多语言、方言、口音、打断等语音场景
